# REALITY.EXE — Backend API

**Real-World Quest Generator and Life Gamification Engine**

A production-quality FastAPI backend that powers a location-based, AI-driven life gamification game. Players receive real-world quests generated by a local AI, go outside to complete them, upload photo evidence for AI verification, and earn XP, level up, and unlock achievements.

## Architecture Overview

```
Client
  │
  ▼
FastAPI (app/main.py)
  │  ┌──────────────────────────────────────────────────┐
  │  │ Middleware stack (bottom-to-top for requests)     │
  │  │  SecurityHeadersMiddleware                        │
  │  │  LoggingMiddleware                                │
  │  │  RequestIDMiddleware                              │
  │  └──────────────────────────────────────────────────┘
  │
  ▼ API v1  (/api/v1)
  ├── /auth          Authentication & JWT
  ├── /player        Profile, stats, progression
  ├── /quests        Quest catalogue, state machine, generation
  ├── /evidence      Secure image upload
  ├── /reflections   AI post-quest reflections
  ├── /achievements  Achievement catalogue
  ├── /history       Quest attempt history
  └── /ai            Provider health check
  │
  ▼ Services (business logic)
  ├── AuthService     Registration, login, JWT issuance
  ├── QuestService    State-machine transitions
  ├── XPService       Deterministic XP + level calculation
  ├── QuestOrchestrator  AI generation pipeline
  ├── AchievementService  Evaluation + idempotent unlock
  ├── HistoryService  Paginated history + extended stats
  ├── CompletionService  Full completion pipeline
  ├── VerificationService  Vision AI evidence analysis
  ├── ReflectionService   AI reflection generation + fallback
  └── ChaosService    Continuation quest chain
  │
  ▼ Repositories (async SQLAlchemy ORM)
  │
  ▼ PostgreSQL  (aiosqlite in tests)
```

## Quick Start

### Prerequisites

- Python 3.11+
- PostgreSQL 15+ (or use `aiosqlite` for tests only)
- [Ollama](https://ollama.com) running locally for AI features

### 1. Clone and set up environment

```bash
cp .env.example .env
# Edit .env — at minimum set DATABASE_URL and AUTH_SECRET
```

### 2. Install dependencies

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
```

### 3. Run database migrations

```bash
alembic upgrade head
```

### 4. Start the development server

```bash
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

## Environment Variables

All settings are loaded via Pydantic Settings from environment variables or a `.env` file.

| Variable | Default | Description |
|---|---|---|
| `ENVIRONMENT` | `development` | Set to `production` to enable production guards |
| `DEBUG` | `False` | Set to `true` in development to enable SQL echo |
| `AUTH_SECRET` | *(dev placeholder)* | **Required in production** — JWT signing secret (≥32 chars) |
| `DATABASE_URL` | `postgresql+asyncpg://...` | Async SQLAlchemy URL |
| `SYNC_DATABASE_URL` | `postgresql://...` | Sync URL for Alembic migrations |
| `OLLAMA_BASE_URL` | `http://localhost:11434` | Ollama server base URL |
| `TEXT_MODEL` | `llama3` | Ollama model for quest + reflection generation |
| `VISION_MODEL` | `llava` | Ollama model for evidence vision analysis |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `60` | JWT lifetime in minutes |
| `MAX_UPLOAD_SIZE_BYTES` | `10485760` | Evidence upload size cap (10 MB) |
| `CHAOS_MAX_CHAIN_DEPTH` | `5` | Max Chaos Mode continuation chain length |
| `ALLOWED_ORIGINS` | `http://localhost:3000,...` | CORS allowed origins |

> **Production**: `AUTH_SECRET` must differ from the default, and `DEBUG` must be `false`. The server refuses to start if these guards fail.

## Quest Lifecycle

Quest attempts follow a strict state machine:

```
CREATED → ACTIVE → POCKET_MODE → RETURNED → EVIDENCE_PENDING → VERIFYING → COMPLETED
              │                       │
              ▼                       ▼
           PAUSED ◄──── resume    ABANDONED
              │
              ▼
          ABANDONED
```

| Transition | Endpoint |
|---|---|
| → ACTIVE | `POST /quests/{id}/start` |
| → POCKET_MODE | `POST /quests/{id}/pocket` |
| → RETURNED | `POST /quests/{id}/return` |
| → EVIDENCE_PENDING | (via `POST /evidence/upload`) |
| → VERIFYING | (via `POST /evidence/{id}/analyze`) |
| → COMPLETED | `POST /quests/{id}/complete` |
| → PAUSED | `POST /quests/{id}/pause` |
| → ACTIVE (resume) | `POST /quests/{id}/resume` |
| → ABANDONED | `POST /quests/{id}/abandon` |

## AI Pipeline

Quest generation goes through a 4-layer validation pipeline before persistence:

```
LLM output
  → JSON parse          (extract from fences/prose if needed)
  → Schema validation   (Pydantic GeneratedQuestOutput)
  → Safety validation   (33 deterministic rules, HARD_BLOCK)
  → Quality validation  (objective clarity, duration, SOFT_BLOCK)
  → Business validation (XP bounds, difficulty enum, SOFT_BLOCK)
  → Persist to DB

On any HARD_BLOCK → immediate fallback (no retry)
On SOFT_BLOCK     → retry (up to AI_MAX_RETRIES), then fallback
Fallback          → curated library of 8 hand-crafted safe quests
```

The Ollama provider uses the `/api/generate` endpoint with a JSON Schema `format` parameter to constrain the model output.

## Security Model

- **Passwords**: bcrypt with per-password salts; constant-time verification
- **JWT**: HS256, 60-minute lifetime, algorithm list enforced (no `alg:none`)
- **IDOR**: every service function validates `user_id` ownership before operating
- **Upload security**: MIME allowlist, extension cross-check, Pillow decode validation, random UUID storage keys, no user input in paths
- **Rate limiting**: slowapi, 200 req/min default
- **Security headers**: `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, conditional HSTS
- **Error responses**: never expose stack traces or internal details
- **Production guards**: server refuses to start if `AUTH_SECRET` is the default value or `DEBUG=true`

## Offline / Idempotency Support

Key endpoints support offline-first clients via:

- **`X-Idempotency-Key` header** — echoed in the response `sync` object
- **`sync` metadata** in responses — `server_timestamp`, `resource_version`, `idempotency_key`
- **XP idempotency** — `XPTransaction.reference_id` prevents double-award for the same event
- **Quest completion** — calling `POST /quests/{id}/complete` twice returns the same result (`idempotent: true`)

## Chaos Mode

Chaos Mode chains multiple quests into an emergent real-world mission:

```
COMPLETED quest
  → player describes discovery
  → POST /quests/{attempt_id}/chaos-next
  → AI generates continuation quest (same safety pipeline)
  → new attempt auto-started
  → repeat up to CHAOS_MAX_CHAIN_DEPTH (default 5)
```

The chain is idempotent — calling the endpoint twice for the same completed attempt returns the existing continuation.

## Docker

### Quick start (development)

```bash
# 1. Copy and configure
cp .env.docker .env
# Edit .env — change AUTH_SECRET and POSTGRES_PASSWORD at minimum

# 2. Start backend + PostgreSQL with hot-reload
docker compose up

# 3. Start backend + PostgreSQL + Ollama (optional AI)
docker compose --profile ollama up
```

### Production

```bash
# Build the production image
docker build --target runtime -t reality-exe-backend:latest .

# Start services (no hot-reload, 2 workers)
docker compose up -d

# Tail logs
docker compose logs -f backend

# Apply pending migrations without restarting
docker compose exec backend alembic upgrade head

# Open a shell inside the running container
docker compose exec backend bash

# Stop and remove containers (keeps volumes)
docker compose down

# Stop and remove containers + volumes (destructive — loses DB data)
docker compose down -v
```

### Ollama model management

Models are NOT pulled automatically. Pull them once and they persist in
the `ollama_models` volume across restarts:

```bash
# Start Ollama service first
docker compose --profile ollama up -d ollama

# Pull the text model (≈4 GB)
docker compose exec ollama ollama pull llama3

# Pull the vision model (≈4 GB)
docker compose exec ollama ollama pull llava

# List available models
docker compose exec ollama ollama list
```

### Services summary

| Service | Port | Purpose |
|---|---|---|
| `backend` | `8000` | FastAPI application |
| `db` | `5432` (localhost only) | PostgreSQL 16 |

### Startup diagnostic

The container runs `scripts/startup_check.py` before starting the server.
It reports database connectivity, AI provider status, and storage
configuration. The server will **not start** if the database is unreachable.
